## 3. 작성 원칙

### 3.1 핵심 원칙

1. **간략 요약형**: 핵심 기능만 간결하게 설명
2. **자체 개발 부분 강조**: 커스텀 모듈, 자체 구현 기능 중심
3. **실제 코드 기반**: composer.json, config/sync, 모듈 코드에서 추출
4. **시각적 다이어그램 포함**: ASCII 다이어그램 사용

### 3.2 작업 진행 원칙

1. **사용자가 "종료"라고 할 때까지 계속 진행**
2. **git commit은 사용자 요청 전까지 절대 하지 않음**
3. **작업 중간중간 진행 상황 보고**

### 3.3 문체 및 표현 원칙

1. **쉬운 설명 우선**: 기술 용어를 나열하기보다 "무엇을 위해 만들었는지" 중심으로 작성
2. **비개발자도 이해 가능한 수준**: 공공기관 담당자가 읽어도 대략적인 내용 파악 가능하게
3. **"왜 이렇게 만들었나" 강조**: 단순 기능 나열이 아닌, 의도와 목적 설명

**좋은 예시**:
> 일반 회원과 관리자 계정을 완전히 분리하여, 외부 사용자가 관리 시스템에 접근하는 것을 원천 차단했습니다.

**피해야 할 예시**:
> user.user 번들과 user.manager 번들을 EntityBundlePluginInterface를 통해 분리 구현하였으며...

### 3.4 언어 규칙

| 구분 | 언어 | 예시 |
|------|------|------|
| 기술 용어 | 영어 (필요시 한글 병기) | JSON:API (데이터 통신 규격) |
| 설명/문장 | 한글 | "사용자 인증을 처리한다" |
| 테이블 헤더 | 한글 우선 | 필드명, 설명, 용도 |

**기술 용어 한글 병기 예시**:
- Headless CMS → 헤드리스 CMS (화면 없는 백엔드 시스템)
- Entity → 엔티티 (데이터 단위)
- Bundle → 번들 (엔티티의 세부 유형)

### 3.3 다이어그램 규칙

- **형식**: ASCII 다이어그램 (```text 블록 사용)
- **도구**: 직접 작성 또는 텍스트 박스 형태
- **예시**:
```text
┌─────────────┐     JSON:API     ┌─────────────┐
│   Drupal    │ ◄──────────────► │    Astro    │
│  (Backend)  │                  │ (Frontend)  │
└─────────────┘                  └─────────────┘
```

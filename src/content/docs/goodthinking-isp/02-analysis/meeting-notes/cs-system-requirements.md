## 기능요건 상세 — 정기구독팀 (SUB)

### SUB-001

| 항목 | 내용 |
|------|------|
| **번호** | SUB-001 |
| **제목** | 개인정보 자동 파기 |
| **내용** | 개인정보 보유 기간 경과 또는 처리 목적 달성 시, 해당 고객 정보를 **자동으로 휴면처리·재동의 요청·마스킹 처리**하는 기능을 구현한다. 파기 대상 목록 자동 추출, 파기 이력 관리(일시·항목·처리자), 파기 전 알림 및 재동의 프로세스를 포함한다. |
| **배경** | 현재 5년 경과 개인정보의 자동 삭제 기능이 없어, 정황규 매니저가 매월 과거 만료자를 엑셀로 추출하여 **일일이 눈으로 대조하며 삭제**하는 수작업을 진행 중. 정기구독팀 인터뷰에서 **"가장 급한 법적 리스크"**로 직접 언급되었으며, 개인정보보호법상 보유 기간 경과 시 지체 없이 파기해야 하나 수동 처리 방식은 누락 위험이 높음. ([R1](/goodthinking-isp/02-analysis/meeting-notes/subscription-team-interview/#시스템-기능-개선-요구사항), [N4](/goodthinking-isp/02-analysis/meeting-notes/subscription-team-interview/#신규-발견-수작업병목)) |
| **관련 시스템** | CS 시스템 |
| **관련 메뉴** | 관리자업무 > 회원 현황 |
| **관련 부서** | 정기구독팀, 경영지원팀 |

:::caution[법적 리스크]
개인정보보호법상 보유 기간 경과 시 지체 없이 파기해야 하며, 현재 수동 처리 방식은 누락 위험이 높아 **최우선 구현 대상**입니다.
:::

### SUB-002

| 항목 | 내용 |
|------|------|
| **번호** | SUB-002 |
| **제목** | 결제·회계 시스템 API 연동 |
| **내용** | ① 나이스페이 API를 통해 **4~5개 분산 계정의 결제 내역을 CS 시스템에서 통합 조회**하고, 카드 결제 취소를 CS 시스템 내에서 즉시 처리할 수 있도록 한다. ② 위하고(WEHAGO) API 연동으로 매출·수금 데이터를 자동 전송하여 이중 입력을 제거한다. ③ **콜센터에서도 본사 이관 없이 직접 즉시 취소 처리** 가능하도록 하며, 취소 권한 등급 설정·취소 사유 기록·취소 이력 관리를 포함한다. |
| **배경** | 결제 출처에 따라 **4~5개의 개별 나이스페이 계정**(담당자 직접입력 카드 / 홈페이지 카드·계좌이체 / 담당자 직접입력 계좌이체 / 예비 / 다양한 기관 상대 결제)을 번갈아 접속해야 하며, 카드 취소 시 해당 계정을 찾아 직접 처리(정황규 매니저 담당). 동일 데이터를 CS 시스템과 위하고 양쪽에 각각 입력하는 이중 작업이 발생하여 업무 피로도가 높음. 콜센터에서 카드 결제 취소 시 본사(정기구독팀)에 이관해야 하며 처리 지연으로 고객 불만 발생. ([R2 정기구독팀](/goodthinking-isp/02-analysis/meeting-notes/subscription-team-interview/#시스템-기능-개선-요구사항), [N6](/goodthinking-isp/02-analysis/meeting-notes/subscription-team-interview/#신규-발견-수작업병목), [R4 콜센터](/goodthinking-isp/02-analysis/meeting-notes/call-center-interview/#시스템-기능-개선-요구사항)) |
| **관련 시스템** | CS 시스템, 나이스페이, 위하고(WEHAGO) |
| **관련 메뉴** | 입금관리 > 카드결제관리, 입금관리 > 가상계좌관리 |
| **관련 부서** | 정기구독팀, 경영지원팀, 콜센터 |

([R3 정기구독팀](/goodthinking-isp/02-analysis/meeting-notes/subscription-team-interview/#시스템-기능-개선-요구사항), [N5](/goodthinking-isp/02-analysis/meeting-notes/subscription-team-interview/#신규-발견-수작업병목), [핵심 발견 #6 영업추진팀](/goodthinking-isp/02-analysis/meeting-notes/sales-team-interview/#핵심-발견-사항), [N7](/goodthinking-isp/02-analysis/meeting-notes/sales-team-interview/#신규-발견-수작업병목)) |

:::

### SALES-005

| 항목 | 내용 |
|------|------|
| **번호** | SALES-005 |
| **제목** | 거래처 관리 기능 (목록 관리 + 코드 통합 + 필터링) |
| **내용** | CS 시스템 내 **거래처 목록을 등록·정리하여 관리**하기 용이하도록 기능을 추가한다. ① 위하고 코드와 CS 코드를 매칭하여 정합성 확보, ② 더 이상 거래하지 않는 품절/절판 거래처는 검색에서 보이지 않도록 필터링(체크박스) 기능 추가, ③ B2B 거래처(다량 특판) 신규 등록 기능 강화. |
| **배경** | 위하고 거래처 코드와 CS 시스템 코드가 다르거나, 같은 업체임에도 이름이 바뀌었다는 이유로 코드가 새로 생성되어 **중복 데이터가 쌓여 있음**. 대부분의 B2B 거래처(다량 특판)가 CS 시스템 내 회원으로 존재하지 않아 시스템 기반 관리 불가. 영업추진팀에서 관리하는 데이터의 핵심키는 위하고 코드임. ([핵심 발견 #7](/goodthinking-isp/02-analysis/meeting-notes/sales-team-interview/#핵심-발견-사항), [#9](/goodthinking-isp/02-analysis/meeting-notes/sales-team-interview/#핵심-발견-사항)) |
| **관련 시스템** | CS 시스템, 위하고 |
| **관련 메뉴** | 거래처관리 |
| **관련 부서** | 영업추진팀, 경영지원팀 |

:::tip[데이터 정합성 우선]
거래처 관리 기능 개선 시, **위하고 코드를 마스터 키로 설정**하고 CS 시스템 코드와 매핑 테이블을 구성하는 것이 권장됩니다. 중복 코드 정리는 데이터 마이그레이션 시점에 일괄 처리 필요.
:::

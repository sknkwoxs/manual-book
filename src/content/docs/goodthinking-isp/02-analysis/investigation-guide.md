# 조사 가이드 및 주의사항

ISP 1단계(현황 분석) 수행 전 반드시 확인해야 할 사항과 리스크 대응 전략입니다.

## 2. 리스크 관리: 외부 개발자 협조 제한

### 문제 상황

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        외부 개발자 협조 제한 시 영향                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ✅ 파악 가능한 것                    ❌ 파악 어려운 것                     │
│   ─────────────────                   ─────────────────                     │
│   • DB 스키마 (역공학)                 • 비즈니스 로직 배경/의도              │
│   • 테이블 관계 (FK 분석)              • 예외 처리 케이스                    │
│   • 데이터 흐름 (데이터 기반 추정)      • 히든 기능/암묵적 규칙              │
│   • 화면 기능 (사용자 인터뷰)          • "왜 이렇게 만들었는지"              │
│   • 현재 업무 프로세스                 • 과거 변경 히스토리                  │
│                                                                             │
│   📌 전략: 파악 가능한 것에 집중하고, 어려운 것은 사용자 검증으로 보완       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 대응 전략

#### 전략 1: 역공학 중심 접근

```
DB 스키마 분석 → 데이터 흐름 추정 → 사용자 검증 → 로직 확정
     (1)              (2)              (3)           (4)
```

**단계별 수행 방법**:

| 단계 | 활동 | 산출물 |
|:----:|------|--------|
| 1 | DB 스키마 덤프, 테이블 목록화 | AS-IS ERD (초안) |
| 2 | FK 관계 분석, 데이터 샘플 확인 | 데이터 흐름도 (초안) |
| 3 | 사용자에게 "이렇게 동작하나요?" 검증 | 검증된 데이터 흐름도 |
| 4 | 불명확한 부분은 "추정" 표기 후 진행 | 최종 분석 문서 |

#### 전략 2: 사용자 중심 분석

**실사용자가 개발자보다 더 잘 아는 것**:
- 실제 업무 흐름 (What)
- 예외 상황 대응 방법 (How)
- 현재 시스템의 불편한 점 (Pain Point)
- 꼭 필요한 기능 vs 안 쓰는 기능

**사용자 인터뷰로 파악할 것**:
```
□ 일일 업무 흐름 (시간순)
□ 자주 사용하는 화면/기능 Top 5
□ 거의 안 쓰는 기능
□ 예외 상황 처리 방법
□ 수작업으로 하는 것들
□ 가장 불편한 점 Top 3
```

#### 전략 3: 최소 정보 요청 전략

외부 개발자에게는 **핵심만 요청**:

```
[필수 요청 - 1회 요청으로 끝내기]

1. DB 스키마 전체 (DDL export)
2. Stored Procedure 전체 코드
3. 시스템 전체 구조도 (있다면)
4. 외부 연동 방식 설명 (간략히)

→ 상세 질문은 하지 않음 (기대하지 않음)
→ 받은 자료로 자체 분석 진행
```

## 3. 역공학 기반 분석 방법

### DB 스키마 분석 절차

```
1. 테이블 목록 추출
   └─ SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES

2. 테이블별 컬럼 구조 파악
   └─ 컬럼명, 데이터타입, NULL 허용, 기본값

3. PK/FK 관계 분석
   └─ 외래키 기반 테이블 관계도 작성

4. 레코드 수 확인
   └─ 활발히 사용되는 테이블 식별

5. 최근 수정일 확인
   └─ 현재 사용 중인 테이블 식별
```

### 테이블 분류 기준

| 분류 | 기준 | 분석 우선순위 |
|------|------|:------------:|
| **핵심 테이블** | 레코드 多 + 최근 수정 | ⭐⭐⭐ |
| **참조 테이블** | 코드성 데이터, 변경 적음 | ⭐⭐ |
| **이력 테이블** | 로그성 데이터 | ⭐ |
| **미사용 테이블** | 레코드 0 또는 오래된 수정일 | - |

### 데이터 기반 업무 흐름 추정

```
예시: 주문 처리 흐름 추정

[주문 테이블]         [고객 테이블]         [구독 테이블]
 - 주문ID (PK)   ───►  - 고객ID (PK)   ◄───  - 구독ID (PK)
 - 고객ID (FK)         - 이름                - 고객ID (FK)
 - 주문일자            - 연락처              - 시작일
 - 상태코드            - ...                 - 종료일
 - 채널코드                                  - 상태

    │                                            │
    └──────────── 추정: 주문 → 구독 생성 ─────────┘
                  (사용자 검증 필요)
```

## 4. 인터뷰 전략

### 인터뷰 대상별 접근법

#### 외부 개발자 (1회, 30분~1시간)

**목적**: 전체 구조 파악, 핵심 포인트만 확인

**질문 예시**:
- "시스템 전체 구조를 간략히 설명해 주실 수 있나요?"
- "가장 복잡한 로직이 어디에 있나요?"
- "외부 연동(Playauto, CMS 등)은 어떤 방식으로 하나요?"
- "이 시스템에서 가장 주의해야 할 부분이 있다면?"

**주의사항**:
- 상세 질문 기대하지 않기
- 답변 안 해도 추궁하지 않기
- 받을 수 있는 자료 요청에 집중

#### 실사용자 - CS팀 (다회, 각 1시간)

**목적**: 실제 업무 흐름, Pain Point 파악

**질문 예시**:
- "하루 업무를 시간순으로 설명해 주세요"
- "이 화면에서 어떤 작업을 하시나요?" (화면 보며)
- "고객 문의가 들어오면 어떤 순서로 처리하시나요?"
- "예외 상황(환불, 오류 등)은 어떻게 처리하시나요?"
- "가장 불편하거나 시간이 오래 걸리는 작업은?"
- "이 기능은 자주 사용하시나요?" (기능별 확인)

**Tip**: 
- 실제 화면을 보면서 진행 (화면 공유 또는 방문)
- 워크 쉐도잉 가능하면 가장 좋음

#### 운영팀/마케팅팀 (각 1회, 30분~1시간)

**목적**: 데이터 활용 현황, 리포트 요구사항

**질문 예시**:
- "현재 어떤 데이터/리포트를 보고 계신가요?"
- "데이터 확인할 때 불편한 점이 있나요?"
- "필요한데 못 보고 있는 데이터가 있나요?"

### 인터뷰 일정 계획 (예시)

| 주차 | 대상 | 목적 | 소요시간 |
|:----:|------|------|:--------:|
| 1주 | 외부 개발자 | 시스템 구조 파악, 자료 수령 | 1시간 |
| 1주 | CS팀 리더 | 전체 업무 흐름 파악 | 1시간 |
| 2주 | CS팀 실무자 A | 주문/고객 관리 업무 상세 | 1시간 |
| 2주 | CS팀 실무자 B | CS 처리/구독 관리 업무 상세 | 1시간 |
| 2주 | 운영팀 | 데이터 활용 현황 | 30분 |
| 3주 | (필요시) 추가 인터뷰 | 불명확한 부분 확인 | - |

## 5. 조사 체크리스트

### Phase 1: 사전 준비 (조사 시작 전)

```
□ 자료 요청
  □ 외부 개발자에게 DB 스키마 요청
  □ 외부 개발자에게 Stored Procedure 요청
  □ 외부 개발자에게 시스템 구성도 요청 (있다면)
  □ CS팀에게 주요 화면 스크린샷 요청

□ 인터뷰 준비
  □ 인터뷰 대상자 리스트업
  □ 일정 조율
  □ 질문지 준비

□ 환경 준비
  □ DB 접속 환경 세팅 (클라이언트 도구)
  □ 화면 녹화/캡처 도구 준비
  □ 문서 템플릿 준비
```

### Phase 2: 데이터 분석

```
□ DB 스키마 분석
  □ 테이블 목록 작성
  □ 테이블별 레코드 수 확인
  □ PK/FK 관계 분석
  □ AS-IS ERD 초안 작성

□ 데이터 흐름 분석
  □ 핵심 테이블 식별
  □ 데이터 흐름 추정
  □ Stored Procedure 로직 분석

□ 데이터 품질 확인
  □ 중복 데이터 확인
  □ NULL 값 비율 확인
  □ 개인정보 항목 식별
```

### Phase 3: 업무 분석

```
□ 인터뷰 수행
  □ 외부 개발자 인터뷰
  □ CS팀 인터뷰 (복수)
  □ 운영팀 인터뷰

□ 업무 흐름 문서화
  □ 주요 업무 프로세스 흐름도
  □ 화면-기능 매핑표
  □ 예외 케이스 목록

□ Pain Point 정리
  □ 현재 불편사항 목록
  □ 수작업 항목 목록
  □ 개선 요구사항 목록
```

### Phase 4: 외부 연동 분석

```
□ 연동 채널 파악
  □ 현재 사용 채널 목록 확인
  □ 각 채널 연동 방식 확인 (API/파일)
  □ Playauto 연동 상세 확인

□ API 스펙 수집
  □ 네이버 스마트스토어 API
  □ (기타 채널 API)
  □ CMS 연동 API

□ 연동 현황 문서화
  □ 현재 연동 구조도
  □ 데이터 흐름 (외부 → 내부)
```

## 6. 불명확한 부분 처리 원칙

조사 중 파악이 어려운 부분이 있을 경우:

### 표기 원칙

| 상태 | 표기 | 의미 |
|------|------|------|
| 확인됨 | ✅ | 담당자/사용자 확인 완료 |
| 추정 | 🔶 | 데이터 기반 추정 (검증 필요) |
| 미확인 | ❓ | 정보 부족으로 파악 불가 |

### 문서화 예시

```
## 주문 처리 프로세스

1. 주문 수집 ✅
   - Playauto에서 주문 파일 다운로드 (CS팀 확인)
   
2. 주문 입력 🔶
   - CS System에 수동 입력 추정 (화면 존재 확인)
   - 자동 입력 기능 유무 미확인
   
3. CMS 권한 부여 ❓
   - 연동 방식 미확인 (외부 개발자 답변 없음)
   - 추가 조사 필요
```

### 리스크 등록

파악 불가 항목은 **리스크 레지스터**에 등록:

| ID | 항목 | 리스크 | 대응 방안 | 상태 |
|----|------|--------|----------|:----:|
| R-01 | CMS 연동 방식 | 설계 시 잘못된 가정 가능 | CMS 담당자 별도 확인 | Open |
| R-02 | 예외 처리 로직 | 신규 시스템 누락 가능 | 운영 후 보완 계획 | Open |

# Utility Tree

Utility Tree는 아키텍처 설계 시 품질 속성의 우선순위를 결정하기 위한 도구입니다. 비즈니스 중요도와 기술적 난이도를 함께 고려하여 **아키텍처 드라이버**를 식별합니다.

:::note[좋은생각사람들 시스템 규모]
- 동시 사용자 약 10~15명 (사내 10명 + 외부콜센터 4명)
- 통합 DB 151 tables, 49개 비즈니스 로직 (20 SP + 14 Function + 15 Trigger)
- 외부 연동 7건 (나이스페이, CJ대한통운, Playauto, 이카운트, CTI, SMS, 우편)
- C/S → Web 전환 (XPlatform → React + NestJS)
:::

---

## Utility Tree 구조

```
시스템 유용성 (System Utility)
├── 가용성 (Availability)
├── 성능 (Performance)
├── 보안 (Security)
├── 변경용이성 (Modifiability)
├── 사용성 (Usability)
└── 운영성 (Operability)
```

### 우선순위 표기법

- **비즈니스 중요도**: H(High), M(Medium), L(Low)
- **기술적 난이도**: H(High), M(Medium), L(Low)
- **표기**: (중요도, 난이도) - 예: (H, M)

> **(H, H)** 시나리오는 **아키텍처 드라이버**로서 가장 먼저 설계에 반영해야 합니다.

## 좋은생각 웹 시스템 Utility Tree

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        좋은생각 웹 시스템 Utility                            │
│   (C/S → Web 전환, 151t 통합, 49개 로직 API 전환, 외부 연동 7건)             │
└─────────────────────────────────────────────────────────────────────────────┘
        │
        ├── 가용성 (Availability)
        │   ├── 시스템 장애 복구
        │   │   └── [A-1] 웹 서버 크래시 시 5분 내 복구 ──────────── (H, M)
        │   │         (AWS ECS 헬스체크 → 자동 재시작)
        │   ├── 외부 연동 장애 대응
        │   │   └── [A-2] Playauto/나이스페이 등 API 장애 시         (H, H) ★
        │   │         재시도 및 알림 (Circuit Breaker 패턴)
        │   └── 데이터 보호
        │       └── [A-3] RDS 장애 시 데이터 유실 0건 ─────────────── (H, H) ★
        │             (Multi-AZ 자동 페일오버, RPO 0)
        │
        ├── 성능 (Performance)
        │   ├── 응답 시간
        │   │   └── [P-2] 고객 조회 2초 이내 응답 ────────────────── (H, M) ★
        │   │         (PT_Customer 48컬럼 + JOIN 5테이블, 동시 15명)
        │   ├── 처리량
        │   │   └── [P-1] 외부몰 주문 50~100건/일 수집 1분 내 ────── (M, L)
        │   │         (Playauto API 폴링 10분 간격)
        │   └── 대용량 처리
        │       └── [P-3] On-Prem+AWS 151t 마이그레이션 4시간 내 ─── (M, H)
        │             (MSSQL→MSSQL 동일 엔진, 스키마 통합)
        │
        ├── 보안 (Security)
        │   ├── 접근 통제
        │   │   └── [S-1] 개인정보 RBAC + 마스킹 ──────────────────── (H, M) ★
        │   │         (외부콜센터 접근, PT_Auth 기반, 개인정보보호법)
        │   ├── 외부 공격 방어
        │   │   └── [S-2] OWASP Top 10 차단 ─────────────────────── (H, M)
        │   │         (PPTP VPN→HTTPS 전환으로 공격 표면 변경)
        │   └── 데이터 유출 방지
        │       └── [S-3] 대량 다운로드 승인 및 로깅 ─────────────── (H, L)
        │             (AuditLog 테이블 기록)
        │
        ├── 변경용이성 (Modifiability)
        │   ├── 기능 확장
        │   │   └── [M-1] 신규 판매채널 5일 내 추가 ──────────────── (M, H) ★
        │   │         (어댑터 패턴 — 현행 네이버/쿠팡 → 11번가 등)
        │   ├── 프로세스 변경
        │   │   └── [M-2] 발송 워크플로우 설정 변경 1일 내 ─────────── (M, M)
        │   │         (상태 머신 기반)
        │   └── 리포트 변경
        │       └── [M-3] 리포트 양식 2일 내 수정 ────────────────── (L, L)
        │
        ├── 사용성 (Usability)
        │   ├── 학습 용이성
        │   │   └── [U-1] 4시간 교육 후 업무 수행 가능 ───────────── (M, L)
        │   │         (현행 C/S 대비 학습 시간 동등 이하)
        │   ├── 오류 대응
        │   │   └── [U-2] 한국어 오류 메시지 + 해결 안내 ──────────── (M, L)
        │   └── 업무 효율성
        │       └── [U-3] CTI 콜~상담 완료 5클릭 이내 ───────────── (H, M)
        │             (정기구독팀+외부콜센터 핵심 업무)
        │
        └── 운영성 (Operability)
            ├── 모니터링
            │   └── [O-1] 이상 징후 5분 내 감지 ──────────────────── (M, M)
            │         (CloudWatch + Sentry)
            └── 장애 대응
                └── [O-2] 배치 실패 시 즉시 알림 및 재실행 ────────── (M, L)
                      (월간지 발송, 지로 생성, 이연수익 등)
```

## 아키텍처 드라이버 (Architecture Drivers)

(H, H) 또는 비즈니스 중요도 H인 시나리오들이 아키텍처 설계의 핵심 드라이버입니다.

### Tier 1: 핵심 드라이버 (H, H)

| ID | 시나리오 | 품질 속성 | 아키텍처 결정 영향 |
|----|----------|-----------|-------------------|
| A-2 | Playauto/나이스페이 등 외부 API 장애 시 재시도 및 알림 | 가용성 | Circuit Breaker 패턴 (NestJS), 재시도 큐 (BullMQ/Redis), 수동 처리 대기열 UI |
| A-3 | RDS 장애 시 데이터 유실 0건 | 가용성 | AWS RDS Multi-AZ (동기 복제), 자동 백업 (일일), Read Replica (조회 분리) |

### Tier 2: 주요 드라이버 (H, M) 또는 (M, H)

| ID | 시나리오 | 품질 속성 | 아키텍처 결정 영향 |
|----|----------|-----------|-------------------|
| P-2 | 고객 조회 2초 이내 (PT_Customer + JOIN 5t, 동시 15명) | 성능 | Redis 캐싱, DB 인덱스 최적화, 페이지네이션 |
| S-1 | 개인정보 RBAC + 역할별 마스킹 (외부콜센터 포함) | 보안 | PT_Auth 기반 RBAC 미들웨어, 필드 레벨 마스킹 Interceptor |
| U-3 | CTI 콜 ~ 상담 완료 5클릭 이내 | 사용성 | 고객 상세 탭 UI, CTI WebSocket 연동, 단일 화면 업무 흐름 |
| M-1 | 신규 판매채널 5일 내 추가 | 변경용이성 | IMarketplaceAdapter 인터페이스, 플러그인 아키텍처 |

## 품질 속성별 우선순위 매트릭스

|  | 높은 난이도 (H) | 중간 난이도 (M) | 낮은 난이도 (L) |
|--|:---------------:|:---------------:|:---------------:|
| **높은 중요도 (H)** | A-2, A-3 | A-1, P-2, S-1, S-2, U-3 | S-3 |
| **중간 중요도 (M)** | M-1, P-3 | M-2, O-1 | P-1, U-1, U-2, O-2 |
| **낮은 중요도 (L)** | - | - | M-3 |

### 우선순위 결정 원칙

1. **(H, H)**: 최우선 - 아키텍처 초기 설계에 반드시 반영
2. **(H, M)**: 높음 - 상세 설계 시 반드시 고려
3. **(H, L)**: 중간 - 구현 시 표준 패턴 적용
4. **(M, H)**: 중간 - 기술적 검토 필요, 대안 탐색
5. **(M, M) 이하**: 낮음 - 일반적인 설계/구현 적용

## 아키텍처 전략 도출

### 1. 가용성 전략

**드라이버**: A-2 (외부 API 장애), A-3 (데이터 보호)

```
┌─────────────────────────────────────────────────────────┐
│                    가용성 전략                           │
├─────────────────────────────────────────────────────────┤
│  • Circuit Breaker 패턴 (Playauto, 나이스페이, CJ 등)   │
│    → NestJS + opossum 라이브러리                         │
│  • 재시도 큐 (BullMQ + Redis)                            │
│    → 외부몰 주문 수집 실패 시 재처리                      │
│  • AWS RDS Multi-AZ (MSSQL)                              │
│    → 자동 페일오버, RPO 0 (동기 복제)                    │
│  • 일일 자동 백업 + S3 교차 리전 복제                    │
│  • ECS 헬스체크 → 자동 재시작 (5분 이내 복구)            │
│  • 배치 작업 재시도 메커니즘 (최대 3회)                  │
└─────────────────────────────────────────────────────────┘
```

### 2. 성능 전략

**드라이버**: P-2 (고객 조회 응답 2초)

```
┌─────────────────────────────────────────────────────────┐
│                    성능 전략                             │
├─────────────────────────────────────────────────────────┤
│  • Redis 캐싱 (ElastiCache)                              │
│    → 자주 조회: 고객 기본정보, 코드 마스터               │
│    → TTL: 5분 (조회), 즉시 무효화 (변경 시)             │
│  • DB 인덱스 최적화                                      │
│    → PT_Customer: 전화번호, 이름, 고객번호               │
│    → PT_Subscribe: Customer_ID + 상태                   │
│    → 복합 인덱스: 자주 사용 검색 조건 조합               │
│  • 페이지네이션 (커서 기반)                               │
│    → 고객 목록, 주문 목록 등 대량 데이터 화면            │
│  • 쿼리 최적화 (TypeORM QueryBuilder)                    │
│    → N+1 방지, 필요 컬럼만 SELECT                       │
│  ※ 동시 15명 규모 — 별도 로드밸런싱 불필요               │
└─────────────────────────────────────────────────────────┘
```

### 3. 보안 전략

**드라이버**: S-1 (개인정보 접근 통제)

```
┌─────────────────────────────────────────────────────────┐
│                    보안 전략                             │
├─────────────────────────────────────────────────────────┤
│  • RBAC (NestJS Guard + Decorator)                       │
│    → PT_Auth + PT_MENU_authority 기반 역할 매핑          │
│    → 6개 역할: 최고관리자, 정기구독, 영업, 경영,         │
│      콘텐츠, CTI담당                                     │
│  • 필드 레벨 마스킹 (NestJS Interceptor)                 │
│    → 역할별 민감 필드 마스킹 규칙 설정                   │
│    → 외부콜센터: 주소 뒷자리, 카드번호 마스킹            │
│  • 감사 로그 자동 기록 (AuditLog 테이블)                 │
│    → TypeORM Subscriber로 자동 캡처                     │
│  • AWS WAF (OWASP 규칙 세트)                             │
│    → SQL Injection, XSS, CSRF 방어                      │
│  • 전송/저장 암호화 (TLS 1.3 + AES-256)                  │
│  • 개인정보 영향평가 (PIA) 수행 필요                     │
└─────────────────────────────────────────────────────────┘
```

### 4. 변경용이성 전략

**드라이버**: M-1 (신규 판매채널 추가)

```
┌─────────────────────────────────────────────────────────┐
│                  변경용이성 전략                         │
├─────────────────────────────────────────────────────────┤
│  • 어댑터 패턴 (IMarketplaceAdapter)                     │
│    → 채널별 구현: NaverAdapter, CoupangAdapter, ...     │
│    → 신규 채널: 인터페이스 구현만으로 추가               │
│  • NestJS 모듈 구조 (도메인별 분리)                      │
│    → customer/, subscribe/, shipping/, finance/ ...     │
│    → 모듈 간 느슨한 결합, EventEmitter 기반 통신        │
│  • 설정 기반 워크플로우 (상태 머신)                      │
│    → 발송 프로세스: 생성→검증→발송→완료 상태 전이        │
│    → DB 기반 설정 (코드 수정 없이 단계 추가)            │
│  • API 버저닝 (URL prefix: /api/v1/, /api/v2/)          │
│  • OpenAPI 스펙 기반 프론트엔드 코드 자동 생성           │
└─────────────────────────────────────────────────────────┘
```

## Tradeoff 분석

### 가용성 vs 비용 — 좋은생각 규모 고려

| 선택지 | 가용성 | 월 비용 (추정) | 권장 | 비고 |
|--------|:------:|:--------------:|:----:|------|
| 단일 EC2 (t3.large) | 낮음 | ~$80 | ❌ | 단일 장애점, 복구 수동 |
| ECS Fargate (단일 태스크) + RDS Multi-AZ | **높음** | ~$350 | **✅** | 자동 재시작 + DB 페일오버 |
| ECS (2태스크) + ALB + RDS Multi-AZ | 매우 높음 | ~$500 | △ | 동시 15명에 과잉 |
| EKS + 전체 이중화 | 최고 | ~$800+ | ❌ | 운영 복잡도 과잉 |

**결정**: **ECS Fargate + RDS Multi-AZ** — 동시 15명 규모에서 자동 복구와 데이터 보호를 확보하면서 비용을 합리적으로 유지. K8s는 불필요.

### 성능 vs 일관성 — 업무 특성별

| 업무 | 처리 방식 | 성능 | 일관성 | 근거 |
|------|----------|:----:|:------:|------|
| 고객 조회 | **캐시 + 동기** | 높음 | 높음 | 전화 상담 중 — 즉시 응답 필요, 최신 데이터 필수 |
| 외부몰 주문 수집 | **비동기 폴링** | 높음 | 중간 | 10분 간격 — 최종 일관성 허용 |
| 결제/환불 처리 | **동기 트랜잭션** | 낮음 | 최고 | 나이스페이 연동 — 데이터 정합성 최우선 |
| 월간지 발송 생성 | **배치 (야간)** | 높음 | 높음 | 대량 처리 — 업무 시간 외 실행 |
| 대시보드 집계 | **캐시 (TTL 5분)** | 높음 | 낮음 | 실시간 불필요, 근사치 허용 |

**결정**: 업무 특성에 따라 혼합 적용. 결제/환불은 동기 트랜잭션 필수, 조회는 캐시 활용, 수집/발송은 비동기/배치.

### MSSQL 유지 vs PostgreSQL 전환

| 평가 항목 | MSSQL 유지 | PostgreSQL 전환 |
|-----------|:----------:|:---------------:|
| 이관 리스크 | ✅ 낮음 | ⚠️ 높음 (49개 로직 변환) |
| 이관 기간 | ✅ 4~6주 | ⚠️ 8~12주 |
| 연간 라이선스 비용 | ⚠️ ~$2.4K~4.8K | ✅ $0 |
| 운영 인력 | ✅ 현행 유지 | ⚠️ 신규 습득 필요 |

**결정**: 1단계 MSSQL 유지 (프로젝트 일정 우선) → 2단계 안정화 후 PostgreSQL 전환 검토 (12~18개월 후). 상세 분석은 [Web 시스템 아키텍처](./web-architecture)의 Database 섹션 참조.

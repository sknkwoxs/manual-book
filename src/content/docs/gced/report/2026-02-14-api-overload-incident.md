## 1. 장애 개요

### 무슨 일이 있었나요?

2026년 2월 14일 오후 2시경, GCED Clearinghouse 웹사이트가 갑자기 느려지거나 접속이 안 되는 현상이 발생했습니다.

원인을 확인해보니, <strong>자동화된 프로그램(봇)</strong>이 서버에 비정상적으로 많은 요청을 보내고 있었습니다. 마치 한 사람이 1초에 수백 번씩 새로고침을 누르는 것과 같은 상황이었습니다.

서버가 이 요청들을 처리하느라 과부하 상태가 되어, 일반 사용자들이 사이트에 접속하기 어려웠습니다. 약 7시간 30분 동안 간헐적으로 서비스가 불안정한 상태로 운영되었습니다.

### 기술적 설명

백엔드 서버(Drupal)에 과도한 API 요청이 유입되어 CPU 과부하가 발생했습니다. 이로 인해 php-fpm(PHP 처리 프로그램) 프로세스가 반복적으로 정지되었습니다.

## 3. 장애 원인

### 직접적인 원인

서버에 비정상적으로 많은 요청이 한꺼번에 몰려서 처리 능력을 초과했습니다.

### 왜 GCED가 공격 대상이 되었나요?

**GCED Clearinghouse는 공격자들에게 매력적인 타겟입니다:**

1. **오랜 역사와 인지도**: 2015년부터 운영되어 온 유네스코 공식 플랫폼으로, 검색 엔진과 AI 학습 데이터 수집 대상으로 널리 알려져 있습니다.

2. **풍부한 콘텐츠**: 5,300개 이상의 교육 자료, 1,990개의 뉴스, 1,370개의 이벤트 등 양질의 다국어 콘텐츠를 보유하고 있어 AI 크롤러(자동 수집 프로그램)의 주요 타겟이 됩니다.

3. **공개 API**: 프론트엔드 웹사이트가 백엔드 서버의 API를 통해 데이터를 가져오는 구조인데, 이 API 주소가 외부에서도 접근 가능하여 악용될 수 있었습니다.

4. **국제기구 도메인**: UNESCO/APCEIU 관련 도메인으로서 신뢰도가 높아 봇들이 우선적으로 크롤링을 시도합니다.

### 근본적인 원인

1. **요청 제한 시스템 부재**: 서버에 "한 사용자당 1초에 몇 번까지만 요청 가능" 같은 제한이 없었습니다. 이를 "Rate Limiting"이라고 하는데, 이 방어 장치가 없어서 무제한 요청을 받아들였습니다.

2. **캐시 우회**: Cloudflare(보안/속도 향상 서비스)의 캐시(임시 저장소)를 거치지 않고 직접 서버로 요청이 전달되었습니다.

### 기여 요인

- 서버 리소스 특성상 대량 동시 요청 처리에 제약 (AWS Lightsail: 4GB 메모리, 2 vCPU)
- 실시간 경고 알림 시스템 부재

## 5. 대응 조치

### 5.1 당일 긴급 조치 (2026-02-14)

장애 발생 직후 서비스 복구를 위해 아래 조치를 시행했습니다.

| 조치 | 설명 |
|------|------|
| Cloudflare 요청 제한 | Cloudflare 서비스에서 특정 IP의 과도한 요청을 차단하도록 설정 |
| 서버 자동 재시작 | 서버가 멈추면 5분마다 자동으로 재시작하도록 설정 (임시 방편) |
| 봇 차단 태그 추가 | 웹사이트에 "봇은 이 사이트를 수집하지 마세요"라는 표시 추가 |
| 캐시 설정 조정 | 데이터 임시 저장 설정을 최적화 |

### 5.2 영구 방어 시스템 구축 (2026-02-15)

다음 날, 같은 문제가 재발하지 않도록 근본적인 방어 시스템을 구축했습니다.

| 조치 | 설명 |
|------|------|
| 요청 횟수 제한 (Rate Limiting) | 한 사용자(IP)가 보낼 수 있는 요청 수를 제한 |
| 사용자 IP 식별 | 실제 사용자의 IP 주소를 정확히 파악하여 개별 제한 적용 |
| 허용 IP 목록 | 내부 관리자 IP는 제한에서 제외 |
| 오류 메시지 개선 | 제한에 걸렸을 때 친절한 안내 메시지 표시 |

#### 요청 제한 설정 상세

**요청 제한이란?**
한 사용자가 일정 시간 내에 보낼 수 있는 요청 수를 제한하는 것입니다. 마치 놀이공원에서 한 사람이 줄을 서지 않고 계속 놀이기구를 타는 것을 막는 것과 비슷합니다.

- **검색 기능**: 1초에 2회 — 검색은 서버 부하가 크므로 더 엄격하게 제한
- **일반 데이터 조회**: 1초에 30회 — 일반적인 페이지 로딩에 필요한 요청
- **동시 접속**: 50개 연결 — 한 사용자의 동시 연결 수 제한

제한을 초과하면 "잠시 후 다시 시도해주세요" 메시지가 표시됩니다.

#### 사용자 IP 식별 방법

Cloudflare를 거쳐 들어오는 요청에서 실제 사용자의 IP를 정확히 추출하도록 설정했습니다. 이를 통해 각 사용자별로 독립적인 요청 제한을 적용할 수 있습니다.

## 7. 교훈 및 개선점

### 대응 과정 요약

1. 장애 발생 후 즉시 원인 파악 및 긴급 대응에 착수하였습니다.
2. 당일 임시 조치를 통해 서비스 완전 중단을 방지하였으며, 다음 날 영구 방어 시스템 구축을 완료하였습니다.
3. 팀 내 신속한 공유를 통해 협력 대응하였습니다.

### 향후 보완 계획

1. **사전 예방 체계 강화**: 요청 제한 등 방어 장치를 사전에 구축하여 유사 장애를 예방하겠습니다.
2. **실시간 모니터링 도입**: 서버 이상 징후 발생 시 즉시 감지하고 알림을 받을 수 있는 모니터링 체계를 마련하겠습니다.
3. **대응 절차 정비**: 유사 상황 발생 시 신속하게 대응할 수 있도록 표준 절차를 문서화하겠습니다.
4. **CDN 캐시 관리 절차 수립**: 장애 복구 후 CDN 캐시에 비정상 응답이 잔존할 수 있으므로, 대응 완료 시 캐시 퍼지를 필수 절차로 포함하겠습니다.
